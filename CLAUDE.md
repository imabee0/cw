# cw

Rust CLI: fuzzy-pick a GitHub repo (personal + every org, most-recent-first), clone it on demand as a bare store, create-or-resume a session worktree on the latest default branch, launch an agent CLI inside it; finishing the last session deletes the store.

## Commands

```bash
cargo build                          # debug build
cargo install --path . --locked      # install the real binary onto PATH — use this, not `cargo run --`, for anything that must reflect a real install (doctor, completions, --dry-run)
scripts/check                        # fast (default): fmt, hakari, clippy, nextest for affected crates — run while iterating
scripts/check gate                   # before every push: + deny, commit lint, doctests, MSRV, cross-target checks this host can do
scripts/check build                  # release binaries + SHA256SUMS into dist/cw/<triple>/ (runs no tests)
cw --help
cw doctor                            # exits nonzero on any failed check; needs a real controlling tty (`script -q /dev/null cw doctor` if testing from a non-tty harness — plain `cw doctor` there fails the terminal check, not a bug)
cw completions zsh                   # source only after `autoload -U compinit && compinit` has run, same as any zsh completion script
cw finish OWNER/NAME SLUG             # remove one clean, pushed session; deletes the bare store when it was the last
cw --repo OWNER/NAME --root PATH --dry-run SLUG   # only non-interactive way to preview clone/fetch + worktree + agent decision with zero mutation
```

`scripts/check` uses its own `target/check` dir (MSRV: `target/check-msrv`), logs to `target/check-logs/<mode>-<stage>.log`, and exits 0 pass / 1 check failed / 2 setup error. On Linux, `gate` cannot check `aarch64-apple-darwin` (libgit2's Secure Transport needs the macOS SDK) and says so; the merge queue checks and tests it on a macOS runner. `cargo test` alone needs none of the extra tools.

## File map

Flat `src/*.rs` plus one `src/tui/` submodule, binary-only crate, no `lib.rs`. The Cargo workspace is `cw` plus `workspace-hack/` (cargo-hakari's generated crate, config `.config/hakari.toml` — never hand-edit its `Cargo.toml`; after any dependency change run `cargo hakari generate && cargo hakari manage-deps`). `build.rs` turns CI's `CI_VERSION_CW` into `CW_VERSION` (the `--version` string; `CARGO_PKG_VERSION` when unset) and sets `CW_RELEASE_BUILD`/`CW_TARGET`. `install/cw.sh` is the curl-pipe installer.

## Conventions

- No `async`/tokio — plain sync `fn main() -> anyhow::Result<()>`; the `tui` event loop is a plain synchronous poll, and background repo discovery is one `std::thread::spawn` + `mpsc::channel`, nothing heavier.
- `#[serde(deny_unknown_fields)]` on `Config` — a typo'd key fails loudly, never silently ignored.
- Every home-dir-dependent test takes an injected path or `HOME` override, never asserts a literal `/Users/...` path.
- New CLI flags: mirror the existing `#[arg(long, global = true)]` pattern for anything `resume`/`clean`/`scratch` should inherit.

## Invariants and gotchas

- **Worktree/branch naming exactly mirrors Claude Code's own scheme** (`flatten_slug`, `.claude/worktrees/<flat>`, branch `worktree-<flat>`) — required for interop with `EnterWorktree`/subagent tooling. Do not change this shape without checking `worktree.ts` first.
- **`cw` always creates worktrees itself** via git2, never shells out to the agent CLI's own worktree flag — this is what makes resume/clean work identically across every configured agent.
- **Repos are bare stores, not checkouts.** `root/owner/name/.git` is a `--bare` clone marked `cw.managed = true`, with a standard `origin` fetch refspec and no local `refs/heads/*` except session branches; `HEAD` is detached at `refs/cw/default` (the fetched remote HEAD) and new sessions branch from it. `remove_one` deletes the store only when it's `cw.managed` and has no worktrees left — never a user's own bare repo, never a legacy full checkout. Default `root` is `$XDG_DATA_HOME/cw/sessions` (disk-backed, not `/tmp`). Fresh clones go to a `.<name>.cw-clone-<pid>` staging dir and are renamed into place (no half-made stores, no clone races). `fetch_default` deliberately never `--prune`s — a merged-and-deleted session branch must stay "pushed".
- **`create_or_resume_worktree` takes the caller's `repo_root`, never one derived from the `git2::Repository`** — git2 reports locations symlink-resolved (macOS `/var` → `/private/var`, symlinked `$HOME`), which would drift from the paths `scan_worktrees` and the dashboard use. `worktree_path_keeps_the_callers_root_through_a_symlink` pins this on Linux too.
- **`remove_one` re-reads lock + work state itself** — never trust the dashboard's earlier snapshot at the destructive boundary. A cw-written lock whose pid is dead is cleared (crash recovery); any other lock refuses.
- **Every worktree create appends `/.claude/worktrees/` to the repo's `info/exclude`**, and `symlink_shared_dirs` appends `/<dir>` for each linked dir. The first matters for full checkouts (scratch, a user-populated `root`): without it the first worktree makes `fetch_and_ff`'s dirty guard reject every future update. The second matters everywhere: a symlink doesn't match a `dir/`-style ignore pattern, so it would read as unsaved work and block `cw finish`.
- **Hooks (`post_clone_hook`/`post_create_hook`) default to unset.** They execute code the cloned repo supplies, not code the user wrote — never flip either default on, never skip the confirm-once-per-repo consent gate in `hooks.rs`.
- **`gh repo list` must always carry `--limit 1000`** (`github.rs::repo_list_args`) — `gh`'s own default of 30 silently truncates discovery.
- **`--org` is a view filter, never a discovery filter.** `github::discover_repos` always lists every org, and that full set is what `repos.json` caches; `dashboard.rs::filter_repos` applies `--org` to both the cached list shown at startup and the refreshed one. Never push the filter back into discovery — a filtered result would be cached and silently hide every other org from later unfiltered runs.
- **Dashboard non-interactivity is gated on `/dev/tty` + `stderr().is_terminal()`, never on `stdin().is_terminal()`** — crossterm's unix backend opens `/dev/tty` directly for its event source (`tty_fd()`, falling back to a std fd only if `/dev/tty` is unavailable — confirmed in crossterm 0.29's source, not assumed), and `tui::mod`'s `CrosstermBackend` renders to stderr, not stdout, so a piped stdin over a real controlling terminal must still reach the dashboard, and `cw | cat` must never receive UI escape codes. `script -q /dev/null cw` allocates a real pty for local testing. A Python `pty.fork` harness has driven it end to end (render, `/` search, `d`/`y` removal, `q`); such a harness must answer crossterm's `ESC[6n` cursor-position query with `ESC[1;1R`, or crossterm errors with "cursor position could not be read".
- **Any `tracing::warn!`/`error!` firing while a `tui::run` session owns the screen would corrupt the frame** — `main.rs::init_logging` gates the stderr half of its tee behind `tui::TUI_ACTIVE` (an `AtomicBool` set for the duration of every `run()` call) so log lines still reach the day log file but never interleave with in-progress terminal escape codes. Route anything the dashboard needs the user to see into `DashboardModel::status` instead of logging it directly (`dashboard.rs::spawn_repo_thread`'s background thread does this for per-org discovery warnings and a stale-cache notice).
- **`tracing_appender`'s `WorkerGuard` must stay a named local bound in `main()`** — dropping it early silently loses buffered log lines.
- Config/cache paths are fixed at `~/.config/cw/config.toml` and `~/.cache/cw/{repos.json,cw.log.*}` (the session `root` default is the one XDG-aware exception) on both macOS and Linux — not `directories::ProjectDirs`, deliberately, to avoid diverging per platform.
- `cw` shells out to `gh` for GitHub API access and the first clone (`gh auth status` must be green), and to system `git` for every later fetch (`GIT_TERMINAL_PROMPT=0`, so it never blocks on a prompt). `cw doctor` checks both.
- **One event-driven GitHub Actions workflow:** `.github/workflows/ci.yml`, triggered only by `pull_request`, push to `main`, and `merge_group` — no schedule, no manual trigger, no Dependabot/Renovate or any other bot. Its `CI_CONFIG` env block (COMPONENTS, TARGETS) is the one place to add a component or target. `changes` decides what runs (docs-only diffs skip everything but `ci-ok`); `gates` (fmt, clippy, commit + PR-title lint, deny + hakari when deps change) runs before everything expensive; PRs test Tier 1 (Linux); the merge queue adds the macOS check + tests, doctests and MSRV; `main` warms caches, then `version` → `build` → `release`. **`ci-ok` is the only required status check** (ruleset on `main`, merge queue on). Never add a second file under `.github/workflows/`.
- **Releases are git tags `cw-vX.Y.Z` and nothing else.** The `version` job bumps from conventional commits touching cw's paths since the last `cw-v*` tag (`feat` minor, `fix`/`perf` patch, `!`/`BREAKING CHANGE` major — minor while the version is 0.x, so 1.0.0 only ever comes from a deliberate hand-made `cw-v1.0.0` tag; anything else releases nothing) and passes it to `build.rs` as `CI_VERSION_CW` — CI never commits a version bump, so `Cargo.toml`'s `version` is only the seed for the first tag and goes stale by design; the tag is the truth. Squash merges take the PR title as the commit subject, which is why the PR title is linted. Release assets `cw-<triple>.tar.gz` (binary at its root) + `cw-<triple>.tar.gz.sha256` (`<hex>  <name>`) are a contract shared by the `build` job, `install/cw.sh` and `selfupdate.rs` — change all three together. The `release` job tags with `GITHUB_TOKEN`, which never retriggers workflows. Legacy `v0.1.x`/`v0.2.0` tags are history; don't touch them. `cw` is `publish = false` (the crates.io name belongs to another crate).
- **Self-update is for release builds only** — `CW_RELEASE_BUILD` is empty for a `cargo install --path .` build, so `selfupdate`'s check skips quietly to a `tracing::debug!` line and the dashboard's `u` key never activates; by design, not a bug. Pre-`cw-v` installs (axoupdater, `~/.cargo/bin`) can't update to `cw-v*` releases; they reinstall once with `install/cw.sh`.
- **A click on a registered hotspot (agent segment, help-line key, mark column, modal button) performs that action; a click on a table row only focuses it; a second click on the same row within 400ms opens it, same as Enter.** Keys and clicks converge on `tui::update::perform` so neither can drift from the other.
- **Any single-char key binding that doubles as filter text must be gated on the *focused pane's* `query.is_empty()`**, same as `q`-quit. `Space` marks/unmarks the focused worktree row when that query is empty and types a space into the filter otherwise; `d` opens the removal confirm for the checked set, or the focused row alone when nothing is checked. Confirm with `y`; worktrees with changed files or unpushed commits are kept unless `f` includes them (`cw clean --force` starts with them included). `n` (new session), `r` (rescan) and `u` (apply a pending self-update) are gated the same way. `/` enters an explicit search mode (`DashboardModel::editing_filter`) in which every letter, shortcuts and `j`/`k` included, types into the filter; Enter/Tab leave it keeping the filter, Esc leaves it clearing the filter. Each pane owns its own query; gating always checks whichever pane `DashboardModel::focus` currently points at. `j`/`k` are always navigation; `←`/`→` always cycle the agent.

## Standards exceptions

- **This repo's own source is hosted on GitHub** (`imabee0/cw`, public, ruleset + auto-merge on `main`) instead of the house Gitea-only default (global CLAUDE.md § Structure and forge). Explicit, repeated user direction for this one project. Do not migrate this to Gitea without the same explicit direction.
- **`.github/workflows/ci.yml` is the only Actions workflow,** hand-written (no cargo-dist, no release-plz). Third-party actions in it are SHA-pinned with a version comment; tools come from `taiki-e/install-action`, never `cargo install`; no `RUSTFLAGS` or linker settings in the workflow (they belong in `.cargo/config.toml`).
